# KOOS-V1-FEAT-033: image upload, two directions, editable designs

**Ticket:** [KOOS-V1-FEAT-033](https://app.clickup.com/t/123qy9rtnj2) (urgent)
**Design references:** Figma `KO-OS-Upload-Picture---Edit-with-AI` node 14-1643; the ticket's HTML prototype (a front-end mock, every AI action faked locally).
**Decided with Oluwaseyi, 2026-10-21:**

1. **Editor:** a free-form layer editor, built in phases.
2. **Directions:** two different concepts, not one concept drawn twice.
3. **Edit with AI:** uses the app's existing model, `getModel("strategy")`.
4. **Old variants:** at the Calendar and Design Studio entry points, the two editable directions replace the 1-3 route variants. Model-drawn variants are no longer produced there.

## Why a new design model

Today one generation produces one `DesignSpec`, the short structured description of a design (`src/lib/design/spec.ts`). It is rendered by five fixed flexbox layouts (`render/layouts.tsx`) through satori. Elements have no positions, so nothing can be dragged, resized or rotated. On top of that, the background plate is never stored, so changing one word costs a new image-model call.

The fix is a **layer document**: an absolutely positioned list of elements.

- Generation builds it from the spec.
- The editor (phase 2) mutates it.
- One renderer draws it in both places:
  - **On the server:** satori turns it into PNG.
  - **In the browser:** the same JSX renders as DOM.

Satori renders a subset of HTML/CSS. Restricting the renderer to that subset makes the editor and the export agree by construction. A canvas library (Konva, Fabric) would need a second renderer and a parity test it could never fully pass. That is why the editor is DOM + `react-moveable` and not `react-konva`.

## Phases

| PR | Scope |
|---|---|
| **1 (this spec)** | Image choice (own image or KO imagery), upload with preview/remove/replace, two directions as layer documents with a "why this works" list, results screen, PNG and JPG download, regenerate. Calendar post and Design Studio entry points. |
| 2 | Editor: canvas select/drag/resize/rotate/snap, Design and Layers panels, undo/redo, versions (save, restore, up to 30), format switch. Text fit while editing is a browser estimate (font-metric advance widths read from the same TTFs satori loads, with 1em assumed for any glyph the font lacks, so emoji and CJK estimate wide, never narrow). The server re-fits with the satori measurer on save, and the saved document is the server's. Decided with Oluwaseyi 2026-10-21: the server measurer costs 0.4-1.3 s per probe set, too slow for every keystroke. |
| 3 | Edit with AI: free-text and chips, scope (whole design or selection), proposal preview with changed elements outlined, brand checks, accept/decline/try again, accept saves a version. |

## PR 1 contracts

### `src/lib/design/document/schema.ts`: `designDocumentSchema` (zod), version 1

```
{
  version: 1,
  width, height,              // canvas px, from canvasFor(aspectRatio)
  background: string,         // CSS colour
  elements: Element[]         // array order is z-order, first is bottom
}
Element (shared):
  id, name, x, y, width, height, rotation (deg), opacity (0..1), hidden, locked
  type "image":  asset: AssetRef, fit "cover"|"contain", crop {zoom>=1, focusX 0..1, focusY 0..1}, radius
  type "shape":  fill (colour or linear-gradient), borderColor, borderWidth, radius
  type "text":   text, role "headline"|"subheadline"|"cta"|"footer"|"body",
                 font "heading"|"body", fontSize, fontWeight, lineHeight, letterSpacing,
                 align "left"|"center"|"right", italic, color
  type "button": label, fill, color, radius, fontSize, fontWeight
  type "logo":   asset: AssetRef, backing: colour|null
AssetRef = { key: string }    // an R2 storage key, never a URL
```

- **Keys, not URLs.** An asset is referenced by storage key. The server resolves keys to bytes for satori, and the client resolves them to signed URLs.
- **Pinned prefixes.** Keys are accepted only under `logos/`, `generated/` and the new `design-images/` prefix. This is the same pinning `storageKeyFrom` already enforces, so a document can never point the renderer at an arbitrary host.
- **Decoded once.** `storageKeyFrom` refuses a decoded key that a second read would change: a leftover `%` (double encoding), `?`, `#`, `\`, an empty segment, control or invisible characters, or a malformed escape. Legacy keys outside the canonical alphabet still resolve.
- **Canonical keys.** A key must also be in the shape the app mints (`isCanonicalKey` in `src/lib/storage-keys.ts`): letters, digits, `.`, `_` and `-` in non-empty `/`-separated segments, no dot segments. A stored key never passes through a URL decoder, so `%2e%2e`, `//host`, `?`, `#` and invisible characters are refused outright rather than decoded.
- **Pinned canvas.** `width` and `height` must be one of the `canvasFor` sizes. Element geometry is bounded to two canvases in any direction and type to a third of the longest edge, so no document can ask satori for a 10000 px raster.

### `src/lib/design/document/render.tsx`

`documentElement(doc, assets: Record<key, dataUri|url>, fonts) → ReactElement`.

- Only CSS satori supports: `position:absolute`, `display:flex`, `transform: rotate()`, `opacity`, `borderRadius`, `objectFit`, `backgroundImage: linear-gradient`.
- No browser-only properties.
- Greedy line wrapping only, with `word-break: break-word`. `text-wrap: balance` breaks lines differently in satori and Chromium, so balancing is done by the builder (it narrows the box), the one rule both engines agree on.
- `break-word` only on a line at least `minBreakableWidth` wide: the run's longest grapheme cluster in code points, times `MAX_GLYPH_EM` (4 em, the widest advance a face may have) plus tracking. `font-file.ts` measures every glyph of a face, not the ones a cmap range is expected to reach, from every place satori's parser takes an advance: hmtx for all glyphs including `.notdef` (drawn for a code point no face covers), the charstring width of every CFF glyph (which replaces the hmtx advance once the glyph is drawn), and pair kerning (GPOS PairPos and the kern table), held to glyph plus widest kern within 4 em. A face past it is refused at upload and again whenever any face is loaded for a render (a stored brand face, a vendored face, the Google fallback for one), so the render keeps the bundled faces and reports why. Satori never returns when it has to break a line narrower than one grapheme cluster, so a box an edit drags narrower than that overflows instead of hanging the renderer.
- **No render can hold the server.** Every satori and resvg call that draws copy runs in a pool of worker threads (`render/satori-pool.ts`, `satori-worker.cjs`; 2 by default, `KOOS_RENDER_WORKERS` up to 8) with a wall-clock limit per render. A render past it is terminated and rejects with `RenderTimeoutError` (`RENDER_TIMEOUT`), and a fresh worker takes its place; the other workers keep drawing, so one stuck document never stalls another tenant's render. The job does not retry a timed-out render. Overhead is about 0.4 ms per text probe and 1 ms per full 1080x1350 render. A grapheme of stacked combining marks wider than its line looped satori forever before this.
- **Copy is checked at the schema boundary** (`document/text-safety.ts`): normalised to NFC, then refused with a typed fault the user can read when the renderer cannot draw it correctly. Satori has no shaping, bidi or mark positioning, so Arabic (throws), Hebrew (drawn backwards), Devanagari and the other Indic scripts (bare viramas), Thai (stacked marks collide) and Khmer (empty boxes) are refused (`TEXT_SCRIPT_UNSUPPORTED`), as is an accent with no precomposed letter such as Yoruba ẹ́ (`TEXT_ACCENT_UNSUPPORTED`). Armenian, Georgian and polytonic Greek are refused too: satori draws them, but from fallback faces a browser does not pick, so the editor drew them up to 46 px past the box. Normalising also composes Hangul typed as jamo into syllables and removes what draws nothing: text-presentation and variation selectors, tag characters outside the three subdivision flags, and joiners outside a real emoji sequence (at most 4 people). After that every cluster of several code points is either an emoji sequence satori draws as one 1em picture or is refused: more than 2 marks or jamo that form no syllable (`TEXT_CLUSTER_TOO_COMPLEX`), or an accent with no precomposed letter (`TEXT_ACCENT_UNSUPPORTED`). `cluster-fuzz.smoke.test.ts` generates clusters from every kind of code point a cluster can be built from and draws each one the schema keeps at the narrowest width words still break in. Direction overrides and control characters are refused (`TEXT_CONTROL_CHARACTER`), and so is a piece of an emoji on its own (a single flag letter, a skin-tone swatch, the keycap mark or a joiner at the start of a cluster) and an accent with no letter before it: satori joins every emoji word of a design into one string before splitting it into pictures, so a loose piece attaches to the emoji before it and becomes a picture nobody counted (loose flag letters in two runs made 25 flags; 19 hands and 5 loose tones would make 95). Line breaks are stored as `\n`: next/og failed to rasterise a design where `\r\n` was followed by an emoji. A run holds at most 24 emoji, and a whole document at most 24 distinct ones; next/og fetches one picture per distinct emoji grapheme, so the cap counts distinct clusters. That count is the message the user sees, not the cost guard: predicting next/og's fetches from the text took five review rounds and each found another way they disagreed. The guard is in the render worker (`satori-worker.cjs`): it counts the emoji pictures each render asks for and refuses the one past `MAX_EMOJI_FETCHES_PER_RENDER` (24, pinned equal to the schema's cap), so the render fails with `EmojiBudgetError` instead of fetching it. next/og caches a picture only once it loaded, so a refused render leaves nothing blank for the next (`emoji-budget.smoke.test.tsx`, which also renders round 6i's bypass as raw copy and sees it refused). `emoji-fetch.test.ts` holds the schema's count shape by shape (`emoji-shapes.ts`: plain and text-default pictographs with and without VS16, skin tones on bases and on any pictograph, people and pictographs joined to tools and to each other, couples with and without a heart and with two tones, people holding hands with tones, untoned families of three and four, gender signs, hair, keycaps in both spellings, flags, subdivision flags): 24 distinct clusters of each parse and 25 are refused, dealt over all eight runs with every separator, and no loose piece (a tone with or without VS16, a flag letter, a joiner, the keycap mark, VS16, a tag) survives behind an emoji after a line break or at the start of any run. `emoji-fetch.smoke.test.ts` renders the accepted designs through a cold copy of the bundled next/og with fetch stubbed and asserts every request it makes, at least one and at most 24. `specTextFault(spec)` gives the job the same fault before it builds; `documentFromSpec` raises it as `DocumentTextFault` when a caller skipped that.
- **Cost is bounded by count, not just size** (`DOCUMENT_LIMITS`): at most 18 elements, and per type 2 images, 5 shapes, 8 text runs, 2 buttons and 2 logos, per role 2 headlines, 2 subheadlines, 2 CTAs, 3 footer lines and 3 body runs, 2 gradient fills of at most 5 stops, 600 code points of copy in all (a run at most 400) and 24 distinct emoji. The costliest document the caps allow (`testing-cost.ts`: the copy budget in the densest Han glyphs, at the largest size, rotated over every element) draws in 2.1-2.5 s alone and 2.2-2.8 s two at once on the pool (10-core dev machine, 2026-10-23 and 2026-10-24, with other work running). The 3 s bound is checked by `corepack pnpm bench:document-cost` (periodic lane: run it on an idle machine before shipping any change to `DOCUMENT_LIMITS` or the renderer; it exits 1 over the bound), not by a gate test, because wall-clock time failed the gate suite whenever the machine was busy. The gate, `cost.smoke.test.ts`, holds what is deterministic: the worst case still draws, alone and two at once, and two gates hold the bounds. `cost-bounds.test.ts` drives every bound through the real parser: each numeric bound the schema declares (read from the schema with `z.toJSONSchema`), the copy lengths, every count `DOCUMENT_LIMITS` sets, the copy budget, gradient stops and both emoji caps parse at the bound, come back unchanged, and are refused one step past it; each cap is tried again with the load spread over every element that can carry it (every text role, both buttons, gradients on shapes and buttons) and the one-too-many on each in turn; and every case runs in every look a text run can take (italic or not, heading or body face, each alignment, the lightest and heaviest weight). No element number may lack a floor and a ceiling. Every loosening reviewers have tried (a union branch, a transform, a refinement edited or deleted, a cap counted over only some elements, roles, faces or styles) fails it; it is a test of the shapes it builds, not a proof that no rewrite of the refinements could loosen a cap elsewhere, so a change to `limitIssues` or `text-safety.ts` is a review item. `cost.smoke.test.ts` compares the declared bounds with `cost-bench.json`, which `corepack pnpm bench:document-cost --record` writes only when both figures are under the bound, with a digest of the caps it timed: a careless edit of the caps fails the gate, but an edit that also recomputes the digest passes, so a change to `cost-bench.json` that no bench run produced is a review item too. Rewrites that change no bound (`.lte` for `.max`, `z.coerce` with the same limits) pass both gates; they cost nothing. The worst case is built from the schema's own extremes (reach, type size, leading and tracking low ends, border width, radius, crop zoom), so the bench times whatever the schema allows. `rasterizeDocument` reads each asset's header and refuses, before it decodes anything, one over `MAX_DOCUMENT_ASSET_EDGE` (4096 px) on a side or one whose size it cannot read, with `DocumentAssetError`: an 8192 px image took 3.5 s and 5.2 GB to draw. The JPEG reader (`png-dimensions.ts`) accepts only segments written back to back, so a stray byte, a stuffed `0xFF00` or a second start-of-image or frame header between them makes the size unreadable rather than letting the reader land on a fake header the decoder skips. Uploads reach it already fitted to 2560 px and logos to 1024 px; a generated plate must be fitted to the same 2560 px before it is drawn, because an image model's 4K output (about 3072 x 5504 at 9:16) is refused here. Text probes run under a 10 s limit in production; tests pass `TEST_PROBE_LIMIT_MS` (60 s) because the limit also spends a cold worker's start and fallback-face fetches, which a loaded machine stretched past 10 s with no loop present. A process's first render also pays the handshakes for the fallback faces and emoji next/og fetches, about 2 s whatever the emoji count, which the render limit bounds. An `rgb()` channel over 255 is refused, not clamped.
- The same function runs in the editor. `browser-parity.smoke.test.ts` draws every builder output in Chromium and in satori and holds both inside every box. The editor must turn off kerning and ligatures (`SATORI_SHAPING`, satori applies neither), serve CJK from Noto Sans JP inside the brand families (unicode-range U+3000-30FF, U+4E00-9FFF, U+FF00-FFEF), and register its colour-emoji face as a family of its own, `EMOJI_FONT_FAMILY`, sized to a 1em advance. Every run lists that family after the brand's (`textRunStyle`; satori skips a family it has no face for), so a browser draws a whole cluster the brand cannot (ZWJ sequence, flag, keycap, pictograph) as one emoji picture, as satori does, and a plain © or ↔ in the brand face, as satori does. A unicode-range emoji face inside the brand family drew keycaps as the brand's digit plus a combining keycap, 18 px past the box.

`rasterizeDocument({ doc, assets, brand, logoInk?, fonts? }) → { bytes, document, logoFault, brandFontFault }` goes through `createBrandRasterizer` and `logoBackingOnGround` in `render/rasterize.ts`, the same two functions the flex composite uses. One brand-font fallback and one logo-backing measurement, shared.

### `src/lib/design/document/from-spec.ts`

`documentFromSpec({ spec, palette, canvas, image: AssetRef|null, imageFacts?, subject?, logo, measurer }) → { document, copyFault, subjectFault }`.

- **One builder per existing layout**, one file each under `document/builders/`: `hero-center`, `split-left`, `banner-bottom`, `quote-card` and `stat-highlight`, over shared geometry, copy stack and footer.
- **Explicit geometry:** each builder computes boxes for the same zones the flex layout produces today, from canvas width and height, with the flex layouts' own `HEADLINE_STEPS`, `BANNER_BAND` and `footerBandHeight`.
- **Text that fits:** sizes are fitted by laying the copy out through satori itself (`measure.tsx`), so it is exact for the PNG. Every run is measured 2% narrower than it is drawn, which is the room Chromium needs. It needs `next/og`, so it runs on the server; the editor's in-browser estimate and the re-fit on save are PR 2 (table above).
- **Copy faults, never silent:** below the type scale, copy shrinks toward a legibility floor (1.9% of the short side); below the floor a word breaks instead. Either is reported in `copyFault` (`COPY_SHRUNK`, `COPY_WORD_BROKEN`, or `COPY_TOO_LONG` when even that overflows), for the job to surface as a quality fault.
- **Card layouts hold the image inside the card**, clipped to its rounded corners, on a flat ground. A cut-out sits whole in the top of the card with the copy below it, stepping its share of the canvas down (42%, 36%, 30%) before it would ever be laid under the copy; a photograph fills the card with the copy anchored low over its measured veil. The stat card's border is drawn again over any picture inside it, so a subject frame that starts at the card's top edge never covers the border (round-4 live critic, the regenerated stat card).
- **The footer does not repeat the CTA or a line of the copy above it, and never loses a fact.** `footerLinesFor` (render/footer.ts, shared with the flex renderer and the judge) drops a footer item that is the CTA, part of it, or contains it with no fact of its own (a number, a day or month, an address, a proper noun); an item with a fact is kept whole ("Call 0803 555 0142 to book a table"). It keeps what follows a CTA used as a label ("Order on WhatsApp: 0803..." keeps the number) unless the CTA leads into a clause ("Order now and save 20%" stays whole), and starts a line that lost its first item with a capital unless it starts with an address or a mixed-case name ("iOS"). Against the headline and subheadline only a whole line said there word for word is dropped: offers, conditions, exclusions and list items are never cut ("Free delivery in Lekki" stays under "Now baking in Lekki").
- **The headline keeps the hierarchy when room is short.** When the headline would have to leave its type scale, the stack is laid out again with the quote mark, button and gaps at `COMPACT_SCALE` (60%), and the larger headline wins, so a 21px headline never sits under a 160px quote mark.
- **Headlines avoid a lone last word.** When the balanced headline ends on one word, the builder takes one more line at the same size if the zone allows (`widthWithoutOrphan`).
- **Ink, not the line box, is kept inside the element.** The measurer reads how far each run's glyphs reach above and below its line box (`inkExtent`), so Vietnamese stacked capitals and emoji pictures stay inside their elements in both engines.
- **The subject is kept clear and large** (`document/subject.ts`). `documentFromSpec` takes an optional `subject: {x, y, w, h}` in image shares; a cut-out's comes from its alpha bounds. Every layout keeps the headline, subheadline, CTA, accent rule, quote mark, footer lines and logo out of the subject grown by 2% of the short side, and draws the subject whole with its longer edge at least 35% of the canvas's shorter side (a 1080 post seen at 360 px on a phone still shows the product 126 px across). A layout tries its alternative arrangements (copy low, copy high, subject in a band above the copy, a photo inset in a smaller rounded frame when its subject cannot be whole edge to edge, then the mirrored logo corner) and otherwise reports `subjectFault` (`SUBJECT_COVERED` or `SUBJECT_CROPPED`); it never overlaps silently. An inset photo never runs under the logo: the mark sits wholly on the ground. It lines up with the copy: on the canvas axis under centred copy (hero-center), from the text column's left edge under flush-left copy (banner-bottom). A subject box out of range, with a NaN, or under 2% of the image on a side is refused with `SubjectBoxFault` (`SUBJECT_BOX_INVALID`), never clamped or dropped. A cut-out's box is read from alpha with the matting's veil and debris (specks, hairlines, patches under 5% of the subject's weight) left out. The headline leads: when it would fall under 1.5 times the footer's type, the footer drops to its smallest size first, then a card's subject steps down to 70% of its minimum (with `SUBJECT_CROPPED`), and only then does the headline shrink. The CTA label is never under 2.6% of the short side. `measureSubject(doc, imageSize, subject)` is the same rule as a measurement for the job and the eval.
- **Images, measured:** `imageFacts` comes from `measureImage(bytes)` (`document/image-facts.ts`). A cut-out (transparent PNG) is contained and sized by its visible pixels, never cropped. Copy over a photograph gets a veil graded to each run of copy (`builders/scrim.ts`): each run needs the least alpha at which every pixel of its own box clears its target (3:1 for large type, 48 px or 37 px bold; 4.5:1 otherwise), the veil rises into each run no steeper than 2.4 alpha per box height and over at least 25% of the box into its peak, never as coincident stops. Of white, the brand's text colour and near-black, the text colour whose veil changes the photo's lightness (CIE L*) least is used, so a pale sky over dark stone takes dark type over a light veil instead of a grey slab. Hero-center without a subject sets its copy low or high, whichever needs the lighter veil. Dark type and no veil on a bright photo, white type and no veil on a dark one. Without facts, the photo is treated as the worst case.

### Generation (`src/lib/jobs/run-design-generation.ts`)

New request field `image: { source: "upload", key } | { source: "ko" }`. Its presence selects the directions path. Without it, generation keeps today's behaviour, so other callers are unchanged.

1. **Two specs from one model call.** One `generateObject` returns `{ directions: [DirectionSpec, DirectionSpec] }`. A `DirectionSpec` is a `DesignSpec` plus `rationale: string[]` (2 to 4 short reasons, shown as "why this works").
   - The two must differ in layout. Code enforces it: when the model repeats a layout, the second direction gets the first layout not used by the first direction and not in recent layout memory.
   - Each direction also names the brief's product (`productName`, which must be in the brief, and `productLook`, what it looks like), or "" when the brief names none.
   - **Written to length, only the brief's facts** (round 2). Copy and reasons over their limit, stating a number, day, month or claim the brief and brand never gave (`inventedFacts` in `src/lib/jobs/directions/claims.ts`), or a reason claiming a position, size, light, colour or type, go back to the model once, in one call, to be rewritten whole. What still fails is never cut inside a clause and never gets an ellipsis: whole clauses are kept when they still say something, otherwise a headline falls back to the brief's title and a subheadline, button, footer line or reason is left off.
   - **Only the brief's facts, word for word** (round 3). `inventedFacts` also knows day abbreviations ("Sat & Sun"), days relative to posting (today, tonight, tomorrow, this week), holidays, "May" beside a date word, ranking and popularity claims ("number one", "#1", "top-rated", "by popular demand", "best"), offers and scarcity ("half price", "buy one, get one", "only", "sold out", "few left"), "ships", "fresh" and "daily". A price or time keeps the word in front of it: "from ₦4,500" or "before 7am" is invented when the brief says "₦4,500 a slice" and "from 7am" (a range licenses its own ends). "Now in a bottle" is invented unless the brief says "now"; "now available" restates a launch. Copy the model left unfinished ("Treat yourself to the") is a fault like any other and goes back to the fit pass.
   - **Every fact the brief gives, on every direction** (round 3, `src/lib/jobs/directions/brief-facts.ts`). The brief's hard facts are drawn on every direction: one that does not state one gets the brief's own words for it in its footer, joined with middle dots within the footer line's limit; a fact that does not fit (three footer lines already, or longer than a line) is recorded on the usage row as left off, with that reason. Coverage is measured again on the delivered copy (`briefFactsDelivered`).
   - **The facts, read by a reader, held by code** (round 5, `src/lib/jobs/directions/brief-read.ts`). Four rounds of hand patterns kept producing a wrong address ("9 Bourdillon Road, Thursday" printed beside the real one), a phone glued to the hour after it or lost before a bare range ("0803 555 0142 9-5"), a handle drawn as a website and a price without its quantity. Reading a brief is judgement on ambiguous text, so one small structured call (`getModel("strategy")`, run beside the directions call, so no added wait) returns the brief's facts as `{kind, text}` (day, date, time, price, quantity, age, place, contact, offer, condition), what it offers (`product`, `event` or `service`, with the brief's shortest whole phrase for it) and the real people it names. Everything after is code (`settleBriefRead`, `settleBriefFacts`): every span must be the brief's own words or it is dropped and recorded; a contact's phone numbers are read by libphonenumber-js (`max` metadata) in the brand's country (`brandRegion`) and must be valid, and the span ends at the number's last digit (", 9" is not an extension of it); an address ends before a day or time that follows it after a comma; a price keeps the unit or quantity that follows it ("NGN 34,000 for a set of four"); the product itself is never a fact; a span inside another is dropped for the longer one. What a design must carry for a fact to count as stated is derived from its kind: a phone number whole on one line between digit-group boundaries, in its own grouping or with the country code or trunk 0 (concatenating every digit of the copy counted "0803 555 014" over "Ages 2-5" as the number); times by value ("7am" or "07:00"); a bare range by its numbers; days and months by name or abbreviation; prices, counts and ages by value plus their unit words; places by number and name, not the street word ("Rd" states "Road"). Footer items that say nothing the headline, subheadline or button does not, that another item already says, or that are only the product's name under copy that names it, are dropped before coverage (`redundantFooterItems`; round 4 repeated the subheadline in five of eleven footers). An unreachable reader costs the facts, never the design, and is recorded (`briefRead.available`). `inventedFacts` stays the deterministic guard on the output. The readers of the copy are English, like the claim checks; copy in another language is the claim check's (below).
   - **Whole words, every phone, nothing lost silently** (round 6). The brief's own words are matched on word boundaries for facts, the offering and people ("2pm" is not in "12pm", "ice" not in "price", "Ada" not in "Adaeze"), and a second reading of the same words takes their next occurrence. A reading in other punctuation, spacing or ordinals is still the brief's ("0803 555 0142" for "0803-555-0142", "15th" for "15"), a phone is matched digit for digit, and a reading that rephrased around the brief's words keeps the longest run of them holding every number it has ("₦4,500 a slice" settles on "₦4,500 per slice"). A reading that still cannot be placed and holds a number, a day or a contact is `unread`: never drawn, checked against each delivered design and recorded in `factsLeftOff` with a quality fault when the design does not state it. A price grows only by a unit noun ("a box", "per 2 hours", "for a set of four", "for two"), never by "an amazing" or "for Saturday's", and no fact ends on a dangling word ("fees for your"). A contact span is one fact per number, with anything glued after the last number read as its own fact; every valid phone number libphonenumber finds in the brief, in the brand's country or one the brief names ("Accra"), is a fact whether the reader returned it or not (`briefRead.phonesAdded`). Coverage never gives up a footer line with a phone, price, time or date for a fact, and counts what each direction states after the last repeat is dropped. Each real person the brief names is a fact every direction must state, in the brief's words with the role it gives them ("With head baker Tunde Okafor"). Footer repeats are read for meaning: "20-min" is "20-minute", "12–6pm" is "12pm to 6pm", and a price the copy above already gives is said; in the footer a price keeps its unit ("₦35,000" beside "8 seats" is not "₦35,000 a seat"). With the reader down, a model's product name that is a shop, an offer, a possessive or a colour and material is not used.
   - **A correction never loses a fact** (round 4). The gate's judge may rewrite copy; `correctionHolds` (`finalize.ts`) refuses a correction that drops any fact the direction stated, as well as one whose copy fails the checks. Coverage is measured per direction on the copy read off the delivered document (`drawnCopyOf`), so a fact the builders or the gate removed cannot be counted: `briefFactsDelivered` is the worst direction's count, `briefFactsByDirection` every direction's, `factsLeftOff` every fact missing from a delivered design with its reason, and a direction missing one carries a quality fault.
   - **The claim check** (round 4, `src/lib/jobs/directions/claim-check.ts`). ### Upload

- **Endpoint:** `POST /api/uploads/presign` with `kind: "design-image"`.
- **Presign accepts PNG and JPEG only**, up to 20 MB, stored under `design-images/{brandId}/{uuid}.{png|jpg}`. WEBP never reaches presign: the browser converts it first.
- **The signature binds the type and the size.** The AWS presigner leaves `content-type` unsigned by default, so the URL signs `content-type` and `content-length` explicitly (`signableHeaders`). Without that, one URL accepts any type up to R2's 5 GB, and the bucket's public domain would serve it. The same signing function serves attachments and documents, so they get the fix too.
  - **What the browser must send:** presign returns the `contentType` it signed. The PUT sends exactly that `Content-Type` and exactly `sizeBytes` bytes (for a design image, `sizeBytes` is the normalised `blob.size`), or R2 answers 403. `uploadToPresignedUrl(url, blob, onProgress, contentType)` in `src/lib/uploads/put-presigned.ts` does this.
  - An untyped `.txt` document (the browser sends an empty type) is signed as `text/plain`, because an empty type cannot be bound.
- **The key is built from the brand row** (`access.brand.id`), never from the request string, so an uppercase UUID that Postgres matches cannot reach `designImageKeyFor` and 500.
- **Normalised in the browser:** before upload the browser re-encodes every image to fit within 2560 px on the long edge.
  - An image with any transparent pixel (PNG or WEBP) becomes PNG, so the transparency survives. Every opaque image becomes JPEG, which is far smaller for photos.
  - **Why:** satori cannot draw WEBP (see `run-design-generation.ts` on "u2 is not iterable"), and phone photos arrive at 7000+ px while the server fits every image to 2560 px anyway, so a bigger upload is bytes nobody draws.
  - **Free fixes:** re-encoding through `createImageBitmap` also applies EXIF orientation, and strips EXIF metadata such as location. A browser that rejects the `imageOrientation` option with a `TypeError` is retried without it.
  - **Too many pixels:** a file whose header declares more than 100 megapixels (a decompression bomb, or a photo no phone browser can hold decoded) is refused before decoding as too large, not as damaged.
  - **Fully transparent:** an image with no pixel above alpha 0 is refused before upload (`blank`), in the same words the loader uses (`TRANSPARENT_IMAGE_REASON`). Round 3 refused these only at generation (critic C6).
  - **Blank or subject-free:** an image that looks blank, or almost all one colour, is refused before upload (`no_subject`, `NO_SUBJECT_REASON`: "it looks blank, or almost all one colour, so there is nothing in it to show. Choose a photo with your product, place or people in it."), by the same check the loader runs; see "Blank and subject-free images" below. Without it a photo of a white sheet became a design's hero (U3 live critic, photo-a).
- **The renderer:** `next/og` (`@vercel/og`) rasterises the satori SVG with sharp, so librsvg and libxml2, whenever `await import("sharp")` succeeds inside it, and with resvg-wasm otherwise. sharp is a direct dependency and resolves from `next`, so production takes the sharp path; `src/lib/images/renderer-rasteriser.test.ts` fails if it stops resolving or loading from where `@vercel/og` imports it, or if `@vercel/og` drops its sharp branch. Every number below is measured on the sharp path.
- **Checking the real file at generation:** the renderer never sees the stored bytes. `loadDesignImage` returns bytes it encoded itself, or a `DesignImageError`.
  - **Why, decoding:** `next/og` is not safe to hand an uploaded file. An indexed PNG whose PLTE length is not a multiple of 3 panics its Rust PNG decoder, and the panic aborts the Node process (SIGABRT, exit 134), which no try/catch contains. Dozens of other well-framed PNGs and JPEGs it draws as nothing, or throws a `TypeError` on. A structural check cannot copy its decoder rule for rule (FEAT-033 upload round-2 critic).
  - **Why, size:** satori inlines each image as one base64 attribute, and libxml2 refuses an attribute over 10,000,000 characters. Bisected: an image of 7,499,820 bytes draws and one of 7,499,821 throws `XML parse error ... Resource limit exceeded` (`RENDERER_MAX_IMAGE_BYTES`). Round 3 bounded pixels but not bytes, so a real 2560 px cutout, exactly what the normaliser sends, passed the loader at 9.4 MB and threw inside `renderCompositeDesign` (round-3 critic B7). The limit is per attribute: two 6.5 MB images in one render draw.
  - **Cheap checks first:** the key, the 20 MB cap, the type sniff (`detectImageType`, PNG or JPEG only, matching the key), the 4096 px cap per side, the JPEG frame type, then the structural pre-filter (`src/lib/images/decode-check.ts`: the IDAT stream inflates to exactly what the header promises; the JPEG has a frame, a scan and an end marker). The pre-filter refuses truncated uploads and decompression bombs before any decoder allocates for them.
  - **JPEG frame types:** only Huffman-coded baseline, extended and progressive frames (SOF0 to SOF2) are accepted, and only one. Lossless (C3), hierarchical (C5 to C7) and arithmetic-coded (C9 to CB, CD to CF) frames are refused as `unsupported_jpeg` ("it is saved in a kind of JPEG most apps can't open. Save it again as a standard JPEG or PNG."), by `jpegHasUndrawableFrame` before decoding, in `loadDesignImage` and in `reencodeImage` itself, so brand logos and JPEGs embedded in SVG logos get it too. Browsers draw none of them, so the normaliser never writes one, and libvips decoded an arithmetic marker over Huffman data as noise without a warning (round-4 critic C3). **C3 confirmed in round 6** (`loadDesignImage` in a fresh process, 5 runs each, 2026-10-22): a 1600 x 1200 baseline photo JPEG with its SOF0 marker rewritten to C9 or CA is refused `unsupported_jpeg` in 5 to 6 ms at 96 to 104 MB, before any decode; the unmodified file is accepted.
  - **The re-encode:** `reencodeImage` (`src/lib/images/reencode.ts`) decodes with sharp 0.35.5 (libvips 8.18.7: libpng, mozjpeg) with `failOn: "warning"` and a 4096 x 4096 pixel limit, fits the result within 2560 px (`NORMALISED_LONG_EDGE`, the normaliser's own bound, so a client that skipped the normaliser gets the same size), and writes a fresh file: PNG stays PNG (alpha kept; adaptive filtering at zlib level 3, a fifth to a third smaller than unfiltered on photographic cutouts, where level 6 took up to 5 s on smooth 2560 px images), JPEG stays JPEG (quality 92, 4:4:4, baseline, Huffman tables not optimised: optimisation buffers every coefficient for a second pass, and under glibc those buffers stayed resident, about 90 MB per encode of a 2560 px image; pixels are identical and files 8 to 16% larger). Every output is 8-bit sRGB with no metadata: 16-bit becomes 8-bit, CMYK and ICC-tagged files are converted to sRGB, and EXIF orientation is applied, so the server shows what the browser showed. `width` and `height` are the output's. sharp never sees an SVG: only bytes that sniff and decode as PNG or JPEG reach it. The libvips operation cache is off (`sharp.cache(false)`): every image is unique, and the cache only held inputs (12 loads of a 4096 px progressive JPEG peaked at 1.35 GB with it, 0.53 GB without).
  - **The byte budget:** every output is at most 6,500,000 bytes (`RENDERER_IMAGE_BYTE_BUDGET`, about 1 MB under the measured limit). An encode over it is redone smaller: a JPEG first at quality 82 then 72, then any format at a smaller size, each step aiming just under the budget by area (ratio between 0.5 and 0.9 of the long edge). Steps stop at 1080 px, the width of every canvas; an image that still does not fit is refused as `too_detailed`. At most 6 encodes per file. A full encode of a dense 2560 px image is thrown away whenever it comes out over budget, so the steps are first walked on a prediction: 8 evenly spaced bands of 32 rows are encoded and scaled up (within 4% of the full size on real cutouts, photos and noise), and only the first step predicted to fit within 115% of the budget is encoded in full. The full encode still decides; a prediction never accepts or refuses. Images under 1024 rows are not predicted. In practice: JPEG photos never step (a 4096 px q95 noise JPEG, baseline, progressive or restart-marked, is 4.9 to 5.1 MB at 2560 and quality 92); real 2560 px cutouts land at 2047 to 2304 px; 4096 px noise lands at 1341 to 1656 px. Nothing under the caps reaches the floor (RGBA noise at 1080 px is 4.7 MB), so `too_detailed` exists for correctness, not because a file is known to hit it.
  - **Blank images:** a PNG with no pixel above alpha 0 draws exactly like no image, so it is refused (`blank`).
  - **Blank and subject-free images** (`src/lib/uploads/subject-check.ts`, framework-free so the browser normaliser and the loader run the same code on the same numbers). Both sides draw the thumbnail with the same code, `subjectThumbnail`: an exact area average of the full-size pixels, in floating point, fitted in 64 px (`SUBJECT_THUMBNAIL_SIDE`). The browser runs it on the canvas it is about to encode (after the white flatten for a JPEG), the server on the pixels the re-encode decoded from the upload. Until round 6 the browser drew its thumbnail with a canvas and the server with libvips, and on a fine pattern the two resamplers alias differently, so one image could be refused on one side and accepted on the other (round-5 review). Three measures on it, with transparent pixels composited on mid grey and alpha counted as a fourth channel so a cutout's silhouette is a subject whatever its colour:
    - **coverage:** the share of pixels more than 24 (of 255, `SUBJECT_DEVIATION`) from the image's per-channel median in any channel. A product on white is a small share far from white; a wall texture is every pixel a little off white, which the downscale averages away.
    - **edge energy:** the mean over pixels of the largest channel's |dx| + |dy|, for structure with no region far from the median.
    - **local contrast** (round 7): the mean over thumbnail cells of the largest channel's standard deviation across the full-size pixels averaged into that cell (0 to 127.5). `subjectThumbnail` keeps each cell's second moment in the same pass as its average, in float64 (in float32 a flat 40 px cell read as a spread of a few levels). The first two measures are taken on the averages, so a pattern finer than a cell, a 6 px checker, 2 px stripes, a 1 px pinstripe every 8 px, averages to flat grey and read as blank (round-6 review, B1: refused on both paths with "it looks blank"). Inside each cell such a pattern keeps its full contrast; a blank has none at any scale. A smooth gradient has almost none either: across one 40 px cell of a 2560 px image it moves a few levels.
    - An image is refused as `no_subject` only when coverage is under 0.2% (`MIN_SUBJECT_COVERAGE`, about 8 pixels of a 64 x 64), edge energy is under 8 (`MIN_EDGE_ENERGY`) **and** local contrast is under 16 (`MIN_LOCAL_CONTRAST`).   - `title`: up to 40 characters, e.g. "Playful product story"
  - `rationale`: 2 to 4 strings, each up to 90 characters

  Both are stored in `design_generations.rationale` as `{ title, reasons, set, slot }`: `set` and `slot` pair a direction with its sibling, so a regenerate finds the direction on screen beside it however often either slot was regenerated (`currentSibling`, over the whole set). The serializer exposes only `title` and `reasons`.
- **`SerializedGeneration`** (`src/lib/design/serialize.ts`) gains:
  - `direction: { title: string; reasons: string[] } | null`
  - `imageSource: "upload" | "ko" | null`
  - `editable: boolean` (`document !== null`)
- **`GenerateArgs`** (`src/components/design/use-design-generation.ts`) gains `image?: { source: "upload"; key: string } | { source: "ko" }` and `regenerateOf?: string` (a generation id; requires `image`). The route validates both, checks `regenerateOf` belongs to the same brand, and passes them through to the job.
- **`JobProgress`** (`src/lib/generation/poll-job.ts`) gains `stage?: "brief" | "imagery" | "render" | "checks"`.
- **Upload helpers:**
  - `src/lib/uploads/normalize-image.ts` (browser): `normalizeImageForUpload(file: File): Promise<{ blob: Blob; type: "image/png" | "image/jpeg"; width: number; height: number }>`. It throws `ImageNotUsableError` with a user-facing message; a fully transparent image is `blank`.
  - `src/lib/uploads/design-image.ts` (server):
    - `designImageKeyFor(brandId, ext)`
    - `isDesignImageKeyFor(key, brandId)`
    - `loadDesignImage(key, brandId)`: returns `{ bytes, contentType, width, height }`, or throws `DesignImageError` with a user-facing message. `bytes` is the server's re-encode, never the stored file, and `width` and `height` are its size after EXIF orientation. Faults: `foreign_key`, `missing`, `too_large`, `not_png_or_jpeg`, `type_mismatch`, `unreadable`, `too_many_pixels`, `too_detailed`, `blank`. The output is at most 2560 px and 6,500,000 bytes.
- **Presign:** `POST /api/uploads/presign` with `kind: "design-image"` returns `{ url, key, contentType }`, the same shape as the other kinds.

### UI

- **Entry points:** every user of the shared `GenerateDesignButton` (calendar item drawer, strategy design brief panel) plus the Design Studio generate action. The flow lives behind `GenerateDesignButton`, so no entry point can skip the image choice.
- **Send to design team** stays: each direction card carries it, keyed per row, with the ticket context the calendar drawer passes today.
- **Legacy rows** (no `direction`) keep opening the existing `DesignPreviewModal`.
- **Flow:** both open the image-choice modal: "Use a specific image" or "Let KO create the imagery".
  - **Upload:** drop zone with click-to-browse, type and size validation, preview with Remove / Replace / Use this image.
  - **Progress:** a four-step progress modal driven by the job's real progress events, with an error state.
  - **Results:** two direction cards, each with the image, "why this works", Download PNG, Download JPG, Send to design team and Regenerate (this direction only, via `regenerateOf`). Editing is phase 2, so the card has no Edit control yet. A placeholder for an unbuilt feature is a lie.
- **JPG:** converted in the browser from the stored PNG on a `canvas`, white-filled first because JPEG has no alpha.
- Every wait follows CLAUDE.md "Every wait gets an affordance".

### Measurable outcome

- **Events:**
  - `design_image_choice` with `{source}`
  - `design_directions_generated` with `{source, directions, quality_faults}`
  - `design_downloaded` with `{format}`
- **Funnel:** image choice → directions delivered → download.
- **Cost:** with `source = upload`, image-model calls per generation drop from 1-3 to 0, visible on the usage row's `renderers` metadata.
